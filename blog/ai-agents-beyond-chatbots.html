AI agents are not chatbots: what Australian businesses need to know

A chatbot answers questions. An agent completes tasks. That difference changes what you can expect, what can go wrong, and which controls matter.

OzAI Digital Published 20 March 2026 Updated 29 October 2026 6 min read
Updated 29 October 2026

Updated. Added approval gates and evaluations as the operational difference, and the distinction between business agents and coding agents. Removed dated model and framework references, and corrected the Privacy Act description to match the enacted obligation.

When most business leaders hear "AI", they think of chatbots. That is understandable: conversational assistants are the most visible form of the technology. But much of the practical value is not in better conversations. It is in agents that can actually do things.

The distinction matters because it changes what you can expect, and what can go wrong. A chatbot answers questions. An agent completes tasks. If you plan around what chatbots do, you will probably underestimate the opportunity and misjudge the risks.

What makes an agent different

A chatbot takes a message, generates a reply and waits. However capable the underlying model, it is working in an input-output loop.

An agent adds three things.

Tool use. Agents act on external systems: databases, APIs, file stores, browsers, email and business applications. They do not just describe the work; they do it. An agent can look up a customer record, generate an invoice, send an email, update the CRM and log what it did, in one workflow.

Planning. Agents break a goal into steps, check progress and change approach if something does not work. This is not fixed if-then logic; the model reasons about the problem as it goes.

Autonomy. Agents can run with more or less independence. Some need a person's approval at each step. Others run whole workflows and escalate only when they hit something outside their limits. The level of autonomy is a design choice, not a property of the technology.

The operational difference: approvals and evaluations

Because an agent changes things, two controls matter far more than they do for a chatbot.

Approval gates. Decide in advance which actions an agent may take on its own and which need a person to approve. Reading a record might be automatic. Sending a customer email, changing a booking or paying an invoice should usually wait for a person, at least until the agent has a track record. Build the gate into the workflow, not into a policy document.

Evaluations. Before an agent goes live, and every time its prompts, model or tools change, run it against a fixed set of test cases with known correct outcomes, including the awkward ones. That is how you know a change made things better rather than different. The same test set becomes the acceptance test at handover.

Two kinds of agent

The word "agent" now covers two quite different things, and it helps to keep them apart.

Business agents run an operational workflow: triaging enquiries, extracting data from documents, handling reception admin. They act on your business systems, usually with staff approving anything that reaches a customer or a system of record. These are what we deliver as workflow builds.

Coding agents write and change software. They work in a repository, propose changes, and run tests. Used without controls they produce code nobody wants to own. Used inside specified issues, automated quality and security gates, independent review and human-approved merges, they are a fast way to build software. That is how we run agentic software delivery.

The rest of this post is about business agents.

Agent topologies

Agents are not all built the same way. The structure you choose depends on the task and how reliable it must be.

Single agent. One agent with a set of tools handles the task end to end. This is the simplest structure and suits focused workflows: processing a support ticket, building a report from several sources, triaging an inbox. Most businesses should start here.

Pipeline. Several agents run in sequence, each handling one stage; the output of one is the input of the next. This suits processes with distinct stages, for example an intake agent that classifies documents, a processing agent that extracts data, and a review agent that checks the result. Each agent is simpler and more reliable because its job is narrower.

Hierarchical. A coordinating agent hands work to specialist agents, reviews what they return and manages the whole. This mirrors a human team and suits work needing different kinds of expertise, such as research, drafting and fact-checking.

Swarm. Several agents work in parallel on parts of a problem, sharing state or passing messages. This is the most complex structure and suits naturally parallel problems: analysing a large document set, watching several data streams, exploring several options at once.

Where agents fit

Some workflows where agents are a good fit:

Accounts payable. An agent receives invoices by email, extracts line items and totals, matches them against purchase orders in the ERP, flags discrepancies for a person, and queues approved invoices for payment. Work that took a person a large share of each day becomes a short review of the exceptions.

Enquiry and support triage. An agent reads incoming tickets, classifies them by urgency and topic, drafts replies to straightforward ones for staff to approve, and routes complex cases to the right specialist with a summary of the customer's history. People spend their time solving problems, not sorting them.

Compliance monitoring. In financial services, agents can check transactions against rules, prepare draft reports for a compliance officer when thresholds are met, and keep an audit trail. For businesses with AML/CTF obligations, where monitoring volumes are high, the human decision stays with the officer.

Property management. Agents handle tenant enquiries, arrange maintenance with tradespeople, summarise leases and flag upcoming renewals, working across email, property software and accounts.

Common pitfalls

Too much autonomy too early. Resist giving agents full independence on day one. Start with the agent drafting actions and a person approving them. Widen its autonomy as the evaluations and the track record justify it. You will catch edge cases before they become expensive.

Weak error handling. Agents work against real systems that go down, return unexpected data or change their APIs. A well-built agent can pause, retry, escalate or roll back. An agent that works in a demo and fails silently in production is worse than no automation.

Too little visibility. You need to see what agents are doing. Log every action, decision and tool call. It is good engineering, and from 10 December 2026 organisations covered by the Privacy Act must describe in their privacy policy the kinds of significant decisions that computer programs make or substantially inform. You cannot describe what you cannot see. See what changes on 10 December 2026.

The wrong structure. Starting with a swarm when one agent would do adds complexity, cost and failure modes. Match the structure to the task; you can grow it later.

Buy, configure or build

There are three broad routes.

Buy an off-the-shelf product. Many CRM, helpdesk and industry platforms now include agent features. They are fastest to deploy and least flexible, and suit standard processes that match the vendor's assumptions.

Configure a workflow platform. Tools such as n8n and Microsoft Copilot Studio let you assemble agent workflows from pre-built parts. This suits teams with capable technical staff who need custom workflows without writing everything from scratch.

Build a custom agent in code. This gives the most control and flexibility but needs software engineering. It is the right choice when the workflow is unusual, the data is sensitive, or nothing off the shelf fits.

Most businesses end up using a mix. Buy where you can, configure where you need to, and build only where you must.
