MCP explained: connecting assistants to your systems safely

Model Context Protocol is an open standard for connecting assistants to tools and data. Here is how it works, how it differs from function calling, and what it does and does not do for governance.

OzAI Digital Published 30 March 2026 Updated 29 October 2026 4 min read
Updated 29 October 2026

Updated. Retitled; model references made vendor-neutral; added that MCP was donated to the Agentic AI Foundation under the Linux Foundation on 9 December 2025; clarified that MCP helps produce an audit trail but does not itself satisfy any legal obligation.

Anyone who has built an assistant that does real work has hit the same problem: every time the model needs to reach an external tool or data source, someone writes a custom integration. Post to Slack? Custom code. Query a database? Custom code. Read files from a shared drive? More custom code. Each integration is bespoke, fragile, and tied to the model it was built for.

Model Context Protocol (MCP) is an open standard for this problem. It defines how assistants connect to external tools and data, and it has become a common way to give an assistant controlled access to business systems.

The problem MCP solves

Before MCP, integration looked like the early web before HTTP. Each model provider had its own schema for describing tools, and an integration built for one could not be reused with another.

That created problems. Integration work was duplicated across projects. Switching providers meant rebuilding every connection. There was no standard way to draw a boundary around what an assistant could reach. And every integration was a separate piece of code to maintain.

For organisations running several assistants across departments, often on different models, this was becoming unmanageable.

How MCP works

MCP uses a client-server design that will be familiar to anyone who has worked with APIs.

MCP servers expose tools, resources and prompts through a standard interface. A server might provide access to a file system, a database, a Slack workspace or a CRM. It declares what it offers, what parameters each tool accepts and what it returns.

MCP clients are the applications hosting the model. When the model needs to look up a customer record, send a message or run a query, the client calls the relevant server.

The protocol handles discovery (the client learns which tools exist), invocation (it calls a tool with parameters) and responses (it receives structured results), all through one well-defined protocol rather than dozens of custom integrations.

A common analogy is USB. Before USB, every peripheral needed its own connector and driver. MCP aims to give any compatible assistant one way to connect to any compatible tool.

MCP, function calling and custom APIs

How does this differ from function calling, which most current models already support?

Function calling is how a model asks for a function to run: "call this function with these parameters". It does not standardise how the function is implemented, discovered or made available. Each application defines its own functions its own way.

MCP sits one level above. It standardises how tools are described, discovered and reached, so a server written once can be used by any compatible client, whichever model is behind it. Function calling is usually the mechanism underneath; MCP adds portability on top.

Custom APIs are the traditional route: build an endpoint, write client code, handle authentication, parse responses, manage errors. It works, but each integration stands alone. MCP removes much of that repeated work.

In practice the three are complementary. MCP servers often wrap existing APIs, and clients use function calling underneath. The value is the shared layer that makes connections reusable.

Why it matters for a business

Portability. A server built for your CRM works with any MCP-compatible client, whichever model provider is behind it. If you change providers, or use different models for different jobs, the connections carry over. That reduces lock-in and protects the integration work.

Narrow boundaries. A server exposes only the operations it defines. An assistant reaching your database through a server that offers "look up order by number" cannot compose arbitrary queries or read tables it has no tool for. The server is a controlled gateway, which suits the principle of least privilege. It is still your job to design those tools narrowly and to keep write actions separate from read.

Composable systems. Because servers are modular and self-describing, you can assemble larger workflows from small, tested pieces: one assistant connected to your CRM, inbox and knowledge base; another to your finance and reporting tools.

An audit trail. When every tool call goes through MCP servers, you have a single logged path for tool access, which makes it much easier to produce an audit trail. MCP does not itself satisfy any legal obligation. It gives you a convenient place to record what was accessed, by which workflow, and when, which helps when you need to answer questions about a system later.

The ecosystem

Anthropic released MCP as an open standard in late 2024, and it has since been adopted well beyond Anthropic's own products. On 9 December 2025 it was donated to the Agentic AI Foundation, under the Linux Foundation, so its governance no longer sits with a single vendor.

Servers now exist for file systems, Postgres and other databases, Slack, GitHub, Google Drive, Salesforce, Jira, Confluence, cloud services and many other platforms, and a growing number of software vendors ship official servers for their own products.

That ecosystem is what makes the standard useful rather than merely tidy. The more servers exist, the less integration work each new workflow needs.

What this means for Australian businesses

First, connecting an assistant to a common system is cheaper and faster than it was. Where a well-maintained server exists, connecting it can take hours rather than weeks. That makes smaller, single-workflow projects viable for mid-sized businesses.

Second, the work lasts longer. Connections built on an open, vendor-neutral standard do not depend on one model provider. As models change, the connection layer can stay put.

Third, it gives you a cleaner control point. A narrow server with logging is easier to reason about, document and review than a model with broad credentials. That helps when you need to describe a system for your privacy policy or your governance register, but it is a design aid, not a compliance answer.
